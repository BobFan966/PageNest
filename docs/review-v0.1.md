## D4：删除记录是否释放提交名额（已确认 A）

发现：R08 规定“总提交上限”，R09 允许删除单条提交，但尚未规定上限按累计接收数还是当前保留记录数计算。这会改变课堂收集何时停止，也决定数据库要维护哪个计数。仅在页面写“最多 50 条”不足以让教师预测删除后的行为。

建议 A：按累计成功接收的正式提交计数。删除只减少当前保留记录数，不恢复提交名额；重试同一逻辑提交不重复占用。达到上限时提示“已达到累计接收上限”；如需继续收集，由拥有者显式提高上限，并仍满足任务开启且未到期的条件。数据页区分“当前记录”和“累计接收/上限”，避免删后总数看似未满却不能提交。

备选 B：按当前保留的正式记录数计算。删除一条即释放一个名额；界面明确“最多保留 N 条”。这一语义更适合持续补录，但上限不能再解释为该任务一共接收过的人次或提交次数。

两种方案都必须在数据库事务中保持配额与写入一致；不能靠先查 COUNT 再插入。A 的累计计数与删除解耦；B 的计数必须随删除和插入一起更新。具体数据库实现留给工程专项，当前只决定用户可见行为。

```text
共同现状：上限 50，已成功接收 50 条，教师删除其中 1 条
  A：当前记录 49，累计接收 50 → 新提交拒绝；原请求重试不占新名额
  B：当前记录 49             → 可再接受 1 条新提交

配额一致性验收：仅剩 1 个名额时，同时发起两个不同的新提交
  顺序甲：提交 X 先完成 → X 成功、Y 达上限，记录和计数只增加 1
  顺序乙：提交 Y 先完成 → Y 成功、X 达上限，记录和计数只增加 1
  任一提交的事务回滚 → 不留下已占用但没有记录的名额
```

验收还包括：上例中的删除后提交行为与所选语义一致；网络响应丢失后用原 key 重试不重复占额；事务失败不返回成功。失败记录只含请求标识、任务和错误分类，不记录完整业务数据；达到上限使用可区分的错误码和用户提示。

已按用户选择 A 更新 R08、R09、计数展示、Task 数据要求和发布验收。后续架构及测试复用这一决定，不重复提问。

### 数据路径与状态

| 路径 | 正常 | 缺失 | 空值/零结果 | 失败 |
|---|---|---|---|---|
| 任务创建与发布 | 登录者保存字段和配置后发布 | 无会话拒绝；无任务/非拥有者不泄露内容 | 缺标题、无有效字段不可发布 | 校验或数据库失败保留界面输入，不返回成功 |
| 公开提交 | 解析、校验、接收条件、事务写入、回执 | 无 key/必填字段拒绝 | 空对象按 schema 判定；数值 0 不能当缺失 | 原 key 重试；写入失败回滚记录和累计数 |
| 列表与详情 | 拥有者范围、筛选、分页后读取 | 无会话或无资源拒绝 | 0 条展示空状态 | 明确读取失败，不能显示成“0 条” |
| 导出 | 拥有者范围、同一筛选、CSV/JSON | 无资源拒绝 | 0 条须明确显示导出范围及计数 | 不将截断或失败的响应表示成完整导出 |

上表是对现有验收约束的路径展开；具体空任务草稿保存及导出空集的表现需在对应专项阶段细化，不据此增加新功能。

```text
草稿 ──发布（配置有效）──→ 收集中 ──教师关闭──→ 已关闭
                              ↑                    │
                              └────教师恢复────────┘
首次发布后不回到可任意改结构的草稿；结构变化按原需求复制任务。

新记录能否接收 = 收集中 AND 未到期 AND 累计接收数 < 上限
截止/满额是接收条件；单纯“恢复”不能绕过截止或累计上限。

收到请求 → 格式/字段检查 → 幂等检查 → 接收条件 → 事务写入 → 回执
              │               │             │          │
            拒绝坏输入     原回执/冲突       明确拒绝    失败回滚
```

这是拟议依赖与数据路径。对已提交请求的重试，原需求已要求返回原回执，不应因关闭/满额再创建记录；删除后的幂等记录生命周期仍须在数据流专项检查，不能推断为已解决。

### 并发与生产失败

D4 已决定累计接收数不能从当前记录 COUNT 推导。对同任务的“接收新记录”和“关闭/调整上限”必须有统一的事务串行化边界；单靠页面按钮置灰或进程内锁不能证明跨进程一致性。

```text
同一任务的接收与关闭（拟议事务边界）：
  接收事务先完成 → 记录持久化 → 关闭事务完成 → 后续新提交拒绝
  关闭事务先完成 → 接收事务读取关闭状态 → 新提交拒绝
测试分别暂停/释放两条路径，确认新请求无法使用关闭前的过期状态。
```

正常规模以原计划 50 客户端、单任务 10,000 条为验收目标，尚未压测。推测 10 倍负载时先检查热门任务的写事务等待、连接池和导出耗时；100 倍时需重新评估容量，不能据此承诺支持。按任务控制写事务不会强迫不同任务共享一把应用全局锁。

单点：数据库故障会同时影响收集和查看；应用故障会影响所有页面。首版用明确错误、服务重启、已确认记录持久化及备份恢复应对，不引入高可用集群。数据库故障不能返回假成功。恢复时间和数据恢复点仍需在部署评审具体化。

本项目尚无应用和数据库迁移可回滚；未来发布按原计划保留上一版本和可恢复备份，在兼容迁移后切换应用，预发布验证登录、提交、导出及恢复；不把切换代码视为数据库恢复。

### D5：开发和验收是否统一使用 PostgreSQL（已确认 A）

发现：当前草案允许本地 SQLite、公开试用 PostgreSQL。两者事务和锁机制不同；在 SQLite 上通过幂等/配额/关闭并发测试，不能直接证明发布数据库上成立。累计数要求使这一差异成为首版核心路径的问题，而非纯部署偏好。

推荐 A：开发、数据库集成测试、预发布和线上统一 PostgreSQL。纯字段校验等无数据库单元测试无需连接数据库。开发启动增加一个本地数据库服务，但避免维护两种并发实现；实际安装方式和数据库版本在实施时核实，不在本轮安装。

备选 B：保留 SQLite 供日常页面开发；涉及持久化和并发的集成验收从阶段 1 起必须使用 PostgreSQL，不能等到发布才验证。优点是页面预览启动轻；代价是双环境配置和兼容边界，SQLite 测试不能计入生产数据库验收。

两种选项都不降低原有可靠性验收，也不增加业务功能。只选择数据库环境策略，不等于授权云资源、费用或部署。

具体建议：在 PostgreSQL 上评估按任务行锁串行化接收、关闭和配额变更，锁内重查状态并将记录和计数同事务提交；任务+key 唯一约束作为数据库防线。该机制仍需工程专项细化及真实测试，不能只凭 ORM 接口存在就判定已正确。

必要验收：空数据库迁移；两账号隔离；同 key 并发只落一条；同 key 不同数据冲突；最后一个名额并发只接收一条；记录写入失败计数不增加；关闭与接收的两种事务顺序；服务重启后记录与累计计数一致。指标包括写入延迟、数据库等待/超时、提交错误分类，日志不含完整 payload。

官方依据（2026-10-24 查阅）：[PostgreSQL 行锁说明](https://www.postgresql.org/docs/18/explicit-locking.html)；[SQLite 事务隔离说明](https://www.sqlite.org/isolation.html)。前者描述行锁及并发等待，后者说明同一数据库一次只有一个写入者。环境统一建议是本次评审判断，不是官方对本项目容量的保证。

## 第 2 节：错误与恢复映射（本轮已完成）

下表将已有需求中的失败行为落到具体路径。错误名称是拟定的领域分类，不是已实现或已核实的框架异常类；框架异常与领域错误的映射在编码时按锁定版本细化。

| 路径 | 可发生的错误分类 | 处理与用户反馈 | 验收依据 |
|---|---|---|---|
| 登录/管理请求 | 未登录、凭据错误、会话失效 | 不执行管理操作；明确需重新登录，不泄露其他账号信息 | R01、会话安全 |
| 创建/修改/发布 | 字段配置不合法、资源不存在、非拥有者 | 不发布无效配置；保留输入并指出字段；不泄露他人资源 | R01—R03 |
| 请求解析 | JSON 格式错误、请求过大、不支持的编码 | 明确格式或大小错误，不将坏 JSON 降级成原始文本写入 | R05、R10 |
| 字段校验 | 必填缺失、类型错误、未知字段、超限 | 返回字段级错误；拒绝入库；数值 0 与空值分开判断 | 字段策略、R03—R05 |
| 接收条件 | 草稿、关闭、已到期、累计已满 | 明确拒绝新的提交，分别说明原因 | R02、R08、D4 |
| 频率控制 | 请求过频 | 显示限流提示及可用的重试时机；不得返回成功或占用名额 | R08、R10 |
| 幂等 | 已存在相同 key、同 key 内容不同 | 同内容返回原回执；不同内容冲突，不覆盖原记录 | 第 6 节接口契约 |
| 数据库事务 | 连接失败、等待超时、事务冲突、提交结果不确定 | 回滚可回滚的事务；不给假成功；客户端保留原 key 重试确认 | 持久化及幂等验收 |
| 列表/详情/搜索 | 数据库读失败、参数不合法 | 区分读取失败与零结果；筛选输入保留，允许重试 | R06 |
| 导出 | 查询失败、序列化失败、传输中断 | 显示失败，不能把部分文件呈现为完整成功；按原筛选重试 | R07 |
| 单条删除 | 非拥有者、提交不存在、删除事务失败 | 无权不删除；失败不假报成功；累计数不回退 | R01、R09、D4 |
| 进程重启/健康 | 服务不可用、数据库不可用 | 不确认新记录；恢复后已确认记录仍可查看和导出 | R10、发布门槛 |
| 备份/恢复 | 备份失败、文件损坏、恢复不可用 | 演练失败不得视为发布门槛通过；保留上一个已验证备份 | 原运维验收 |

原则：按已知错误分类处理，未知异常记录请求标识与操作上下文后作为服务失败返回，不能吞掉异常继续执行。错误日志不保存密码、凭据或完整提交正文；无法确认提交结果时界面只能显示“尚未确认，请重试”，不能把超时解释为数据库必然没有写入。

AI 调用、文件上传、任意 HTML 托管不是首版代码路径，本节不为它们增加后台任务或错误恢复体系。并发冲突、响应丢失、重启和坏输入已有原始验收要求，本轮未发现需要新增产品决定的错误恢复项；继续第 3 节。数据库提交不确定后的删除与重试交叉情况归入第 4 节。

## 第 4 节：数据流与交互边界（本轮已完成）

### 请求与记录生命周期

```text
界面/独立网页输入
  → 解析：缺正文、坏 JSON、请求过大 → 明确拒绝
  → 规范化与校验：保留 0，处理多选，拒绝未知/不合法字段
  → 任务及幂等事务边界：重查状态、重复、累计上限
  → 写记录及累计计数：同事务，任一失败整体回滚
  → 返回提交回执：网络丢失时原 key 重试
  → 管理查询/导出：owner 范围、筛选、分页/编码
  → 拥有者删除单条：当前记录减少、累计计数不变（D4）
                                      │
                                      └→ 删除后原 key 又被重试？D6
```

| 交互 | 边界 | 现有要求可直接确定的结果 |
|---|---|---|
| 提交按钮 | 双击、重试仍在请求中 | 前端禁重复点击；服务器幂等保证只有一条 |
| 提交过程 | 网络超时、关闭页面、切换应用 | 不宣称请求已取消写入；再次重试复用原 key |
| 管理会话 | 请求期间过期 | 不执行未授权变更；恢复登录后重新校验归属 |
| 数据列表 | 0 条、筛选无结果、10,000 条 | 区分空集和错误；服务器分页，不一次加载全部 |
| 收集状态 | 到期、满额、教师关闭 | 拒绝新提交；旧请求的原回执不重复占额 |
| 删除与重试 | 删除后旧网页自动重发 | 现有独立要求存在交叉风险，D6 待决定保留方式 |

### 并发顺序核验

以下是测试规格与拟议防线，不是实测。接收/关闭边界沿用第 1 节，不重复询问；同任务操作通过数据库事务同步，不能依赖不同进程不共享的内存状态。

| 共享状态与竞争 | 顺序一 | 顺序二 | 必须防止的结果及机制 |
|---|---|---|---|
| 同 key 的两个提交 | X 提交成功，Y 取原回执 | Y 提交成功，X 取原回执 | 两条记录/计数加二；任务+key 唯一约束，事务内重查 |
| 不同 key 抢最后名额 | X 先占，Y 拒绝 | Y 先占，X 拒绝 | 超额；任务事务锁内检查并更新累计数 |
| 新提交与关闭 | 提交先完成，关闭后不再收新记录 | 关闭先完成，提交拒绝 | 关闭确认后的新请求仍使用旧状态；锁内重查 |
| 删除与旧 key 重试 | 重试先返回回执，之后删除 | 删除先完成，之后重试 | 删除内容被原请求重新插入；D6 |
| 写入与服务故障 | 提交未成功 → 回滚后可重试 | 提交已成功但响应丢失 → 原回执 | 丢记录/重复占额；持久化事务与幂等约束 |

测试使用两个独立数据库连接和显式暂停/释放点控制完成顺序，再用新请求查询最终状态；不使用随机 sleep 推断并发已覆盖。

### D6：删除内容后保留哪种去重记录（已确认 A）

发现：如果彻底删除 Submission 及其 key，仍开着的旧网页用原 key 重试，服务器可能把已删除内容重新写回，并再消耗一个名额。R09 的删除与 R10 的幂等要同时成立；不能靠缩短重试时间或提示教师“不要重试”解决。

推荐 A：删除业务内容，保留最小幂等记录。保留任务、原 key、用于识别相同请求的内容指纹及原回执所需元数据，不保留完整 payload；旧 key 同内容返回原回执、不重建记录，不同内容继续冲突。回执只确认原请求曾成功，不表示记录仍在后台保留；拥有者界面明确记录已删除。去重记录随任务生命周期保留，首版不开放永久删除任务。指纹的生成与最小保留字段在工程评审中明确，不能把摘要等同于匿名化保证。

备选 B：软删除原 Submission。记录在列表、详情和导出中不可见，但完整内容仍保存在数据库，旧请求可继续去重。无需单独拆分最小幂等记录，不过“删除”需要明确说明只是隐藏，并且后续仍要定义内容清理策略；首版不因此新增回收站或恢复界面。

两种方案均禁止旧 key 重试使数据复活，并遵守 D4 不返还累计名额。它们在内容保留方式上不同，不是允许放弃幂等或删除的可靠性要求。

验收：两个竞争顺序中都不重建记录；删除后后台、导出和当前记录数不含该内容；累计数不变；同 key 重试不再占额；不同 payload 冲突。A 还需直接检查数据库中业务正文已经移除，剩余记录只含批准的最小字段；B 则须确认界面已明确内容仍被保留。

失败可观测性：记录请求标识、任务标识、幂等命中/冲突分类及删除结果，不记录正文；数据库事务失败不显示删除成功，删除后重放也不能被统计成一次新接收。D6 已确认 A，R09、接口契约和发布验收已同步。两条竞争路径都必须在同一数据库事务同步机制内读取和保留幂等信息，不能先删 key 再另起事务补记录。

多选与类型转换是 R03/R05 同时支持字段类型和普通表单编码的必需实现：共享一份校验规则，普通表单对多选保留重复键值并规范为列表；JSON 保留原类型。空值、0、空列表、重复选项和未知字段分别验证，不能照搬参考代码的简单 to_dict 而丢失选项。字段结构改变继续遵守既有“复制任务”策略，不能原地重解释历史记录。

现有要求及 D6 已覆盖本轮发现的数据流缺口；无需再次选择已批准行为，继续第 5 节。

### D12：提交结果未知时是否允许修改原内容（已确认 A）

问题：原需求规定网络重试复用 key，同 key 不同内容必须冲突。如果学生在“暂时无法确认是否收到”时修改得分，随后按重试发送改后的内容，会与原提交发生冲突；若系统悄悄换新 key，又可能把两份内容都接收。应明确当前页怎样保护这次尚未确认的提交。

**推荐 A：冻结这一次提交的原始内容，只重试确认。** 发出请求时保存本次内容快照；请求中及结果未知时，原内容不可改，“重试确认”始终使用原 key 与原快照。提示“暂时无法确认是否收到，已保留本次内容，请重试确认”。确认成功后显示原回执；服务端明确未接收并给出字段错误时，再允许修改并重试。这里决定当前页的交互，不新增学生账号、后台查询接口、离线队列或刷新恢复机制。

**备选 B：允许编辑，但明确作为另一份新提交。** 原次结果仍标记为未知；修改后不能继续使用“重试确认”按钮，而必须明确告知可能已经存在原记录，并由学生选择是否发送新的一份。新逻辑提交使用新 key，不能静默把原 key 换掉。自由度更高，但学生需要理解两次提交的关系，也更容易主动产生两份记录。

两者都保留原有幂等保证，区别是未知状态的编辑方式，不是让 B 违反同 key 内容冲突要求。推荐 A 依据为“错误预防”和“如实呈现系统状态”：在不能确定服务器是否接收时，不把一次确认动作变成另一份提交。两方案定义工作量粗估 human: S / CC+gstack: S；A 的代价是当前这次提交暂不能改，B 的代价是多一组提示与新提交选择。

验收建议：请求中改动控件不能影响已发出的内容；结果未知的重试沿用原 key/原内容；确认成功只显示回执且不重复计数；明确字段拒绝后可以修正。若选 B，另验收保留原次未知提示及明确新提交，不允许偷偷换 key。未得到答案前不改写 R04 或线框的内容锁定行为。

## 工程架构 E1：同任务的并发事务机制（已确认 A）

[P1]（confidence: 8/10，方案缺口）需求第 6 节规定“累计成功接收数与正式提交写入在同一事务更新，不因单条删除回退”，评审记录原第 1 节只建议“在 PostgreSQL 上评估按任务行锁”。缺少确定机制时，不同 key 抢最后名额、关闭与提交竞争、删除与重试可能各用不同同步边界；这是实施前风险，不是已经复现的缺陷。

候选 1A（推荐）：READ COMMITTED 下先取得对应 Task 行锁；同任务的收集、关闭/恢复、截止/配额变更、正文删除保持一致锁顺序。锁后重读权威状态；已存在 key 先按相同内容返回原回执或冲突，新提交再检查接收条件。正文、最小幂等记录与累计计数在一个事务提交，回滚不得占额；锁内不做网络或导出。保留任务+key 唯一约束。锁等待/语句执行均须有界，数据库失败不给假成功，客户端保留原 key 重试；截止时间使用取得锁后的实际时刻，避免排队跨过截止仍放行。隔离级别、时间函数及具体超时值实施前再核对。

候选 1B：以 SERIALIZABLE 隔离级别保护相关事务，发生序列化失败时重试完整事务；同样保留唯一约束、原 key、原内容、原回执语义及有界超时，不能只重试最后一条 SQL。必须额外覆盖重试耗尽与高争用下的失败比例。两者是机制不同，不打完整度分。

两方案均须验证：两连接争最后名额；同 key 相同/不同内容；关闭与提交的两个完成顺序；删除与重放的两个顺序；写入/提交失败；等待跨过截止；不同任务不被应用全局锁串行化。目标沿用原 50 客户端/P95 要求，无压测结果。工作量粗估：1A human 0.5—1 天 / CC+gstack 1—3 小时，1B human 1—2 天 / CC+gstack 2—5 小时；包括事务原型及并发测试，不是交付承诺。

## 工程架构 E3：幂等判断中的“同内容”（已确认 A）

[P1]（confidence: 8/10，契约缺口）需求第 6 节同时要求接受 JSON/普通表单，以及“同 key 不同数据报冲突”。目前没有定义比较原始请求字节还是解析后的字段内容。参考 app.py:1889 使用 get_json，:1895 使用 form.to_dict；后者不能直接作为多选字段解析方案。新应用尚未实现，不能声称已发生冲突。

候选 3B：以原始请求体字节与传输格式计算指纹。同一 key 重试必须逐字节复用原请求体，键顺序、空白或 JSON/表单切换均可能冲突；客户端示例须保存精确的请求体及 Content-Type，不能每次重新拼装。服务端仍独立校验字段并拒绝坏输入，不允许用字节摘要代替校验。

依据（2026-10-28）：[RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) 解释确定性 JSON 表示的用途；[Python json 文档](https://docs.python.org/3/library/json.html) 说明默认解码及自定义解析能力。选 3A 不自动承诺完整采用 JCS；具体库与数字边界须在编码规格中核对。

### E4：内容摘要仍可能泄露低取值答案（技术细节已选定）

### C1：编码规则缺失且重放容易受隐式转换影响（已自行细化）

[P1]（confidence: 8/10）E3 已批准语义比较，但还缺确定规则。仅接受 application/json 对象与 application/x-www-form-urlencoded；不接受原始文本/multipart 附件。submission_key 可在 Idempotency-Key 头或保留的 submission_key 字段提供，二者同时提供必须一致，剥离系统元数据后校验业务字段；TaskField 禁止使用这些系统保留名。JSON 重复键、未知字段、非对象根节点、NaN/Infinity、布尔值冒充数字拒绝。

数字用有限十进制解析并规范为去冗余零的十进制表示，负零归零；JSON 必须是数字，表单按数字字段解析字符串，不进行任意 JSON 字符串强转。首版数字约束候选为总有效位不超过 15、小数位不超过 6，超限明确报错且不截断，编码时以匿名试用样例验证，若不适用返回技术契约调整。文本不 trim、不改大小写、不做 Unicode 归一化，CRLF/LF 的真实差异仍保留；按解码后字符数校验。可选字段未提供、显式 null、数字/选择空值均规范为缺失；文本空字符串与未提供不同，必填文本空串拒绝。多选视为无序集合，按固定选项顺序规范化，拒绝重复及未知选项，空集合在可选时视为缺失；表单重复单值字段拒绝、多选重复键保留所有值后校验。

确定性字节格式不冒称 RFC 8785：构建带版本的类型标记对象，数字用规范十进制字符串且带 number 类型标记，文本带 text 标记，多选为排序字符串数组；按 key 排序、UTF-8、无排版空白，使用标准 JSON 编码器且禁止 NaN。哈希包含 schema 和规范化版本。这样不依赖二进制浮点或第三方 JCS 精度范围，规范字节只用于指纹，不替换用户字段类型。测试以固定输入/字节向量锁定，正常 payload 保持 JSON 数字/字符串/数组的业务类型。

统一响应结构：成功仅含 receipt{id,received_at,schema_version,is_test}；新提交 201，原 key 同内容重放 200，不返回答案或其他人的记录。400 格式/key、415 编码、422 字段、409 key 冲突或状态阻塞（细分 error.code）、413 过大、429 限流、503 暂时不可确认。数据库 commit 失败不返回成功，客户端 5xx/断网保持原 key/快照；明确 422 可修正，沿用 D12。公共 GET collect 为 405，OPTIONS 只做来源预检；表单页只能读字段/说明，不返回正文。CORS 精确回显允许的 origin 与 Vary: Origin，凭据不参与公开提交，拒绝 null/file 来源；无 Origin 的程序请求可写仍受限流，不把 CORS 当认证。

## 工程性能审查（完成方案检查）

### P1：导出全量装内存且一致性边界不明确（已自行细化）

[P1]（confidence: 8/10）计划 R07 及发布门槛要求按同一筛选导出，参考 app.py:2005 使用 .all()，随后 DataFrame 和 BytesIO 多份数据驻留内存；10k×10KB 仅正文就约100MB，不能沿用该路径。新方案由同一 owner/范围查询，在只读 REPEATABLE READ 事务内固定快照，服务器游标分批约200行序列化到权限受控临时文件；不锁 Task、不长时间占写事务。文件完整生成、核对导出行数后结束数据库事务，再发送附件；失败/超时/磁盘满在发送下载头前报错，不把截断生成当完整文件。

快照语义：包含导出开始快照内满足筛选的记录；开始前已删除正文不出现，快照建立后的新提交不加入；快照之后发生的删除不会撤回已授权的这次导出。页面不拿更晚的列表实时计数声称它等于快照数。响应提供快照时间和导出行数/Content-Length；传输断开不得在界面宣称下载完成。JSON 生成合法数组，CSV 正确转义、UTF-8 BOM，并中和公式前缀（含引导空白/控制字符后 = + - @）；测试真实样例边界，不能靠正则粗暴损坏数字语义。

资源初值：单份临时文件1GiB、生成60秒。单Nginx入口用共享连接限制令全站最多1份活动导出（含生成及下载阶段），忙时立即返回429，不在应用worker中排队。导出路由定向到同代码的独立Gunicorn单worker池，普通页面/收集保留2个worker。应用端口不公开，避免绕入口；不另造租约表或队列，每账号上限由全局1份自然覆盖。超预算明确失败，不截断或静默只导前 N 条；初始10k记录基线必须通过，否则调整实现或规格。临时文件不在 static 或公开目录，完成/失败/连接关闭/进程重启后清理，下载保持 owner 授权；测试生成期间异常及实际断连。代价是本地临时磁盘和短时只读快照，先验证才调高目标。

### P2：计数、分页、搜索及连接预算尚未落地（已自行细化）

[P2]（confidence: 8/10）R06/容量目标只定义页面50条；加入 E2 删除凭据后直接 COUNT(*) 会算入已删除或测试记录。Task.cumulative_accepted 单独存储；保留记录计数、筛选计数均经 data.queries，工作台按当前页任务批量聚合，禁止逐任务 N+1。索引至少 owner+创建时间+id、task+key 唯一、正式未删记录的 task+received_at+id 部分索引；测试记录另按相同查询验证，截止字段使用 timestamptz。计数和页面在同次短读快照内生成，排序 received_at,id 稳定，时间筛选 [from,to)，参数绑定与搜索通配符转义。

分页初版 LIMIT 50/OFFSET，10k范围可接受与否用 EXPLAIN ANALYZE/实际延迟判定；不提前做游标分页产品交互。关键词先限定 owner/task/未删/测试范围再搜索文本表示，最大查询长度200、数据库语句有界；没有证据不建立全字段 GIN、全文搜索服务或缓存。典型10KB不是合法硬上限，64KiB请求上限仍生效；额外字段与结构深度按字段schema拒绝。

初始普通页面/收集2个同步worker，每worker池3+溢出1；导出另一个受限worker、池1+溢出0，应用连接上界9，另留迁移/运维连接；部署资源确定后再算总额，严禁每worker复制“大连接池”。写锁等待先设1秒、写SQL3秒、收集请求目标5秒；在锁后用 clock_timestamp 判定截止。写P95仍以原<2秒为验收，达到超时属于可解释失败，不是性能达标。负载报告分成功延迟/所有请求延迟及429/503/锁超时率，同任务与多任务、同IP与多IP分别测；另测两个账号导出叠加50客户端提交，第二份导出明确繁忙，收集仍须达到基线；正常50客户端基线不得靠限流丢弃请求“通过”。
